# Architecture

> Status: draft. It will be updated as the implementation progresses; significant changes are discussed through the process in [GOVERNANCE.md](../GOVERNANCE.md).

## The problem

Coding agents increasingly work in cloud sandboxes: Linux, no display, and no way to scan a QR code to sign in. Today the only way to debug a WeChat Mini Program is WeChat DevTools, which runs only as a desktop GUI on Windows and macOS and requires signing in with WeChat. As a result, an agent that changes a Mini Program **cannot see the page, cannot read the errors, and cannot show that its change works**.

This project lets an agent do the following in any Linux sandbox, with only Node.js and headless Chromium:

1. **Run**: load a Mini Program project and render any page.
2. **Screenshot**: get a stable, reproducible screenshot of the page.
3. **Annotate**: number the interactive elements on a screenshot and map each number to its WXML node, source location and data, so the agent can refer to and act on them.
4. **Debug**: read console output, errors (mapped back to the original source), `setData` updates and `wx.*` API calls, and tap, type, scroll and navigate between pages.

Every capability returns **structured output** (JSON plus image files) rather than a UI meant for human eyes.

## Overview

```
Mini Program project ──► compiler ──► runtime (logic layer, Worker) ◄──► renderer (view layer, page)
                                               ▲                                 ▲
                                               └──── simulator (Vite app: device, page stack, navigation bar, tabBar)
                                                                    ▲
                                              cli / MCP (drives headless Chromium: screenshot, annotate, debug, interact)
                                                                    ▲
                                                               coding agent
```

| Module    | Location            | Responsibility                                                                                                                                                                                                              | Status                                                                            |
| --------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| compiler  | `packages/compiler` | Load the project (`project.config.json`, `app.json`, subpackages); compile WXML to render functions and WXSS to CSS (including `rpx` conversion and style isolation); bundle logic-layer JS with Rolldown, with source maps | WXML, WXSS, page and logic bundles                                                |
| runtime   | `packages/runtime`  | Logic layer: `App` / `Page` / `Component` / `Behavior`, lifecycles, `setData`, event dispatch; `wx.*` APIs whose host capabilities (network, storage, system info and so on) can be replaced with mocks                     | Core, routing, login and auth mocks, file system, network, canvas, interface APIs |
| renderer  | `packages/renderer` | View layer: build the DOM from render functions and data; implement built-in components as Web Components; send user events back to the logic layer                                                                         | Core components implemented                                                       |
| simulator | `apps/simulator`    | Vite app that combines runtime and renderer: device presets, page stack and routing, navigation bar, tabBar; also serves human developers debugging in a browser                                                            | Dev server implemented                                                            |
| cli       | `packages/cli`      | The entry point for agents: the `omr` CLI and an MCP server, driving headless Chromium                                                                                                                                      | Planned                                                                           |

Separating the logic layer and the view layer (Worker plus page) is deliberate: it reproduces WeChat's two-thread model, so timing bugs such as reading the old DOM before the `setData` callback show up as they would on WeChat.

Each page's view layer runs in a sandboxed iframe with an opaque origin, so page code such as WXS cannot reach the simulator shell: the device chrome, other pages and system UI such as consent dialogs. The shell sends the page its compiled bundle and data by message, and the view layer is served as one classic script, since an opaque origin cannot load modules from the simulator without CORS. The shell and the logic layer talk over a private message port handed to the Worker before Mini Program code runs, so that code cannot post messages as the logic layer or the shell. It still shares the Worker's JavaScript realm, so it could tamper with built-ins the logic layer uses, for example to change the result of a consent dialog; running Mini Program code in a realm of its own would close that gap.

## Components across the two layers

- The view layer knows where each custom component is; the logic layer runs its code. After a render that moved, added or removed a component, the view sends a `tree` message: every component in document order, the nearest component above it (through slots), the tag and `class` its owner wrote, and the event bindings on its host and on the elements above it. The logic layer uses it for:
  - `triggerEvent` with `bubbles`, `composed` and `capturePhase`, which follow those bindings, stopping at `catch`.
  - `selectComponent` and `selectAllComponents`: tag, `#id` and `.class` compounds, the descendant, `>` and `>>>` combinators, and comma-separated groups.
  - `relations` (`parent`/`child`/`ancestor`/`descendant`, by path or `target` behavior): `linked`, `linkChanged` and `unlinked`, `getRelationNodes`, and the `moved` lifetime.
- Definitions support the built-in behaviors `wx://form-field` (a form submits the component's `value` under its `name`), `wx://form-field-group` (a form outside the component collects the controls in its template, which it otherwise skips), `wx://form-field-button` (a `form-type` button in its template reaches a form outside it) and `wx://component-export` (with `export`), plus `definitionFilter`, `hasBehavior`, `options.virtualHost` (the host is `display: contents` and takes no class or style), `options.pureDataPattern` (matching fields never reach the view), `componentGenerics` with `generic:` attributes, `componentPlaceholder` and app.json `resolveAlias`.
- Instances also have `selectOwnerComponent`, `groupSetData`, `getPageId`, `getTabBar`, `router` and `pageRouter`, the `error` lifetime and the `resize` and `routeDone` page lifetimes. Pages get `onResize`; App gets `onPageNotFound` (for a launch page that does not exist) and `onUnhandledRejection`.
- With `tabBar.custom`, each tab page renders the `custom-tab-bar` component fixed at the bottom of its window instead of the shell's tab bar. Its instance exists before the page's `onLoad`, so `this.getTabBar()` works in `onShow`.
- The capsule's menu button opens a sheet: 发送给朋友 when the page has `onShareAppMessage`, 分享到朋友圈 with `onShareTimeline`, 收藏 (`onAddToFavorites`) and 重新进入小程序. A share button and the menu both show the share's title and path in a confirmation sheet.

## App and route events

- `api/app.ts` holds the app-level APIs. The logic layer drives their events: `wx.onError` (`{ message }`), `wx.onUnhandledRejection` and `wx.onPageNotFound` hear what the matching `App` callbacks hear. `onLazyLoadError`, audio interruptions, `onApiCategoryChange`, the keyboard events and `onWindowStateChange` keep their listeners but never fire, since the simulator has no on-screen keyboard. `wx.onAppShow`/`onAppHide` and `wx.onThemeChange` are described under the background and DarkMode below.
- Route listeners fire in the order of WeChat's route listener guide, with one `routeEventId` per route and paths with a leading `/`. A page's view creates it asynchronously, so `onBeforePageLoad`, `onAfterPageLoad` and `onAppRoute` fire when its view is ready, and `onAppRouteDone` after its first render. `wx.rewriteRoute` works only synchronously inside `wx.onBeforeAppRoute`, and only to a page the route's type can open; the launch route can be rewritten too, such as away from a missing page before `onPageNotFound`.
- `wx.enableAlertBeforeUnload` makes the navigation bar's back button ask first; `wx.navigateBack` is not held up, as on WeChat.
- Work these APIs need done in the page, such as `wx.loadFontFace` (`global` fonts also reach pages opened later), `wx.hideKeyboard` and `wx.getSelectedTextRange`, goes to the view as a `viewRequest` and comes back as a `viewReply`.
- `wx.createBufferURL` stores the bytes as a temporary `http://tmp/` file, so images, audio and the file APIs read it like any other.

## Animations, observers and component contexts

- `wx.createAnimation().export()` gives one action per `step()`; the view plays an exported `animation` attribute with CSS transitions, step after step, and does not replay the same export. `this.animate` and `this.clearAnimation` run Web Animations on the elements a selector matches in the caller's template and call back in the logic layer.
- `IntersectionObserver` (`relativeTo`, `relativeToViewport`, margins, thresholds, `initialRatio`) is measured in the view after renders, scrolls of the page or a scroll-view, and resizes; `relativeTo` nodes need not be ancestors. `MediaQueryObserver` uses `matchMedia` in the page and calls back once with the current state, then on changes.
- `VideoContext` drives the page's real `<video>`, including seeking, fullscreen and danmu. `<video>` draws WeChat's controls itself (center play button, a bar that hides while playing, its own full screen button) instead of the browser's. Full screen, from either side, also sends `videoFullScreen` from the view through the logic layer to the shell, which grows the page's WebView over the status bar, navigation bar, capsule and tab bar; the view does not report that window's resize to the page. `MapContext` drives the simulated `<map>` (see below). `CameraContext.takePhoto` and `LivePlayerContext`/`LivePusherContext.snapshot` return generated images. The logic layer reaches a built-in component with `callBuiltin`, answered by `builtinResult`.
- The simulator's file endpoints answer `Range` requests, so media elements can seek in project files and temporary files.
- `<map>` is a simulated map without tiles: the simulator has no map data and fetches none, so it draws a plain base (darker in DarkMode) with a latitude/longitude grid, a scale bar (`show-scale`), a compass (`show-compass`) and a "模拟地图" watermark. Markers (default pin or `iconPath`, size, anchor, rotate, alpha, zIndex), `callout` (BYCLICK/ALWAYS), `label`, `customCallout` with `<cover-view slot="callout">` children, `polyline` (dotted, arrows, border, `colorList`), `polygons`, `circles` (meters at the map's latitude), `controls`, `include-points` and `show-location` (at `location` of `omr.config.json`) are drawn at their Web Mercator positions. Dragging pans, the wheel and a double tap zoom, firing `regionchange` (`begin`/`end` with `causedBy` gesture, drag, scale or update), and taps fire `markertap`, `callouttap`, `labeltap`, `controltap`, `polylinetap` or the map's `tap` with `latitude` and `longitude`. `MapContext` calls the map through `callBuiltin`: it moves (`moveToLocation`, `includePoints`), answers positions and regions, animates `translateMarker` and `moveAlong`, and adds and removes markers; layers, arcs, ground overlays, marker clusters, collisions, POIs, satellite, traffic, 3D, rotate and skew gestures, and `openMapApp` succeed without drawing anything.

- `<web-view>` opens its `src` over the page, in an iframe the shell lays where the page's WebView is, under the navigation bar (which `navigationStyle: custom` does not hide) showing the web page's title. Each web origin is served by its own proxy port on the simulator's server, which forwards every path to the real origin, so the page keeps its paths, history, cookies and same-origin requests, and runs at an origin other than the simulator's. The proxy sends WeChat's user agent upstream (with `MicroMessenger` and `miniProgram/<appid>`), drops `Content-Security-Policy` and `X-Frame-Options`, and injects `WeixinJSBridge`, `window.__wxjs_environment = "miniprogram"` and the user agent at the top of each HTML document, so the JSSDK (jweixin) runs unchanged. The back button goes back in the web page's history first. `bindload` fires with the real URL of each document, `binderror` with `url` and `fullUrl` when the page cannot be reached (the web-view shows an error page). `wx.miniProgram.navigateTo`, `redirectTo`, `switchTab`, `reLaunch` and `navigateBack` route from the web-view's page; `postMessage` collects messages, which `bindmessage` receives together when the page unloads, the web-view is removed, or the page is shared or its link copied from the capsule menu (复制链接). `onShareAppMessage` gets `webViewUrl`, and `WeixinJSBridge.on("onPageStateChange")` hears the app leave and come back. The JSSDK APIs a web-view may use answer as on iOS or Android (by device): `checkJsApi`, `chooseImage` (local ids whose data `getLocalImgData` returns; `uploadImage`/`downloadImage` keep them on the simulator), `previewImage`, `getLocation`, `openLocation`, `getNetworkType` and `scanQRCode`; `config` is not verified, voice, beacons and cards fail as not implemented, and other APIs fail as not supported in `<web-view>`. The proxy ports listen only on the local address the browser reached the simulator at (on both `127.0.0.1` and `::1` when it is a loopback address, since `localhost` may resolve to either), so a web-view works in a browser on that machine (such as the agent's headless Chromium) but not through a single forwarded port. Browsers keep cookies by host, not port, so all proxies share one cookie jar: each origin's cookies, whether its server or its scripts set them, are stored with names prefixed for that origin and without `Domain`, and each proxy sends its origin, and the bridge's `document.cookie` shows its scripts, only that origin's cookies under their own names. Cookies keep `Secure`, which browsers honor over http on loopback hosts only, so a web-view reached at another address loses its secure sessions rather than sending them in clear text. A `src` that is not http(s) shows the same error page as an unreachable one, and fires `binderror`.
- The simulator's server fetches the URLs a Mini Program names for `wx.request`, `wx.downloadFile`, `wx.uploadFile` and network images (its request proxy), and the web pages of `<web-view>`. It does not limit where they go, since a Mini Program under development usually calls a backend on `localhost` or the local network, but it serves both only to clients on this machine: the dev server listens on the network, and a request from another machine gets 403, so it cannot use the developer's machine to reach their local services. A port forward that arrives at a loopback address, such as an orb portal, counts as this machine. Other sites open in a browser on this machine cannot use them either: the request proxy, the file system and `<web-view>`'s proxy answer 403 to requests a browser marks as coming from another site (`Sec-Fetch-Site`), and to POSTs without the content type the simulator sends, which another site cannot send without a CORS preflight.

## Files, canvas and the window

- `wx.*` APIs live in modules under `packages/runtime/src/api/`, one per area (files, network, canvas, interface, device, media). They share the callback and Promise conventions in `api/common.ts` and the host and helpers, such as the privacy check, in `api/context.ts`. An API the simulator does not have fails with `<name>:fail not implemented in the simulator` and a console warning.
- The Mini Program's file system (`wxfile://usr`, temporary `http://tmp/` files and saved `wxfile://store_` files) lives on the simulator server for the life of the dev server, like a device: user files survive reloads. The logic layer reaches it synchronously over `POST /__omr/fs`, as the `*Sync` methods need, and pages show its files by URL through `GET /__omr/fs/file`, so `<image src="http://tmp/...">` works. Code-package files are read-only.
- The Mini Program draws on canvases in the logic layer, on an `OffscreenCanvas`, and each changed picture goes to the `<canvas>` in the page as an `ImageBitmap`. This covers `<canvas type="2d">` (the `node` of a selector query), the legacy `wx.createCanvasContext`, `wx.createOffscreenCanvas` and `wx.canvasToTempFilePath`. Network images (`Canvas.createImage` and the legacy `drawImage` with an `http(s)` URL) load through the request proxy, as WeChat loads them without CORS. `Canvas.toDataURL` reads the pixels and encodes a PNG synchronously in JS (uncompressed, so data URLs are large); other types also give PNG.
- `<scroll-view>`: with `enhanced`, `show-scrollbar` is on unless set to false, and `dragstart` waits until the finger has moved 5px, so a tap fires no drag events; scroll views without `enhanced` show no scrollbar, as phones show none at rest. Tapping the status bar (iOS devices; on Android, double-tapping the title) scrolls vertical scroll views with `enable-back-to-top` back to the top, and, as WeChat does since 2.27.3, those at least 90% of the window's height unless it is set to false.
- `NodesRef.node` of a `<scroll-view enhanced>` gives a ScrollViewContext (null without `enhanced`, as on WeChat); the view keys the element the query found, so the context reaches it without an id. Setting `scrollEnabled`, `bounces`, `showScrollbar` or `pagingEnabled` applies to the scroll view until the attribute of the same name changes; `scrollTo` (`top`, `left`, `animated`), `scrollIntoView` (a selector in the scroll view's template), `triggerRefresh` (fires `refresherrefresh`) and `closeRefresh` work, and `triggerTwoLevel`/`closeTwoLevel`, which are Skyline only, do nothing.
- `<progress active>` moves the bar to `percent` at `duration` ms per percent (30 by default), from 0 (`active-mode="backwards"`) or from where it is (`forwards`), and fires `activeend` with `curPercent`; without `active` it jumps. Only a new `percent` or turning `active` on plays it again.
- `<navigator target="miniProgram">` calls `wx.navigateToMiniProgram` (`app-id`, `path`, `extra-data`, `version` as `envVersion`, `short-link`), `wx.navigateBackMiniProgram` (`open-type="navigateBack"`) or `wx.exitMiniProgram` (`open-type="exit"`) as the tap's user gesture, and fires its `success`, `fail` and `complete` with their results. `wx.exitMiniProgram` puts the Mini Program in the background, as the capsule's close button does.
- `<picker-view>`: every item of a column is as tall as the indicator, whose height `indicator-style` or `indicator-class` sets (34px by default), as WeChat sizes the children of `<picker-view-column>`.
- `<official-account>` shows a follow card of `config.officialAccount.name` only when the launch scene is one WeChat allows (1011, 1017, 1025, 1047 or 1124; open the simulator with `?scene=1047` to launch from a scanned code) and the app came back from a scene that keeps it; otherwise it takes no room and fires `binderror` with `status` 5. A second one on a page fails with `status` 6, and `config.officialAccount.status` makes it fail with another. `<channel-video>` and `<channel-live>` draw a WeChat Channels card with their ids; `<channel-video>` without `feed-id` or `feed-token` fires `binderror`.
- `<page-meta>`: `page-style` replaces the body's style while the room kept for a custom tab bar stays on the root element. `<navigation-bar>`'s `color-animation-duration` and `color-animation-timing-func`, like `wx.setNavigationBarColor`'s `animation`, fade the bar to its new colors. Not simulated: `page-orientation` and `pageOrientation` (the simulated phone stays in portrait), and `background-color-bottom`, which shows only when iOS bounces past the bottom.
- Accessibility: `aria-*` attributes pass through to the elements, and `aria-role` also sets the standard `role`, so a `<view aria-role="button" aria-label="提交">` is a button named 提交 in accessibility snapshots.
- `<input>` and `<textarea>` `cursor-color` colors the caret; `green` is WeChat green (`#07c160`) and `default` keeps the system color.
- `<live-player>` and `<live-pusher>` draw a moving picture instead of a stream. `<live-player>` plays an RTMP or FLV `src` (codes 2001, 2002, 2008, 2026, 2003, 2004; any other address -2302), and `<live-pusher>` asks for `scope.camera` and `scope.record` when inserted (a refusal is `error` 10001 or 10002), previews (1003) and pushes to an RTMP `url` (1001, 1002, 2027, 1008). Both fire `netstatus` every second while they run, their contexts drive them, and the background suspends them (6000 and 5000) until the app comes back.
- `wx.joinVoIPChat` joins a simulated room (privacy agreement, `scope.record`, and `scope.camera` for a video room) with the user and `config.voip.members`; the others take turns in `onVoIPChatSpeakersChanged`, a second join fails with `errCode` -1, and going to the background ends it through `onVoIPChatInterrupted` (-1). `<voip-room>` shows the user's simulated camera (`mode="camera"`) or a member's video (`mode="video"`) while in a video room; without subscribing it shows only the first two members, `subscribeVoIPVideoMembers` picks others, and outside a room or for an openid not in it, it stays black and an inserted window fires `error`.
- `wx.createAudioContext` drives the legacy `<audio>` with its id: `setSrc` (a package path resolves as the template's `src` does), `play`, `pause` and `seek`, which take no callbacks and fire the component's events.
- A focused `<input>` or `<textarea>` raises a simulated keyboard (336px on iPhone 15, 260 on iPhone SE, 300 on Pixel 7; typing still comes from the computer's keyboard). `focus` and `keyboardheightchange` report its height, as `wx.onKeyboardHeightChange` does; with `adjust-position` (default) the page moves up until the field and its `cursor-spacing` clear the keyboard and the field's `<keyboard-accessory>`, which shows on the keyboard, at most 200px tall. Moving focus to another field keeps the keyboard up; taps on the accessory, or on the page while a `hold-keyboard` field has focus, keep the focus.
- Tapping an image in `<editor>` shows the controls its `show-img-*` attributes ask for: the image's size (`show-img-size`), a corner that drags its width with the height following (`show-img-resize`), and a toolbar that aligns its line left, center or right or deletes it (`show-img-toolbar`). Each change fires `input` and can be undone. Focusing the editor raises the simulated keyboard, as inputs do.
- `<functional-page-navigator>` opens functional pages only inside plugins, which the simulator does not run; it shows its children, a tap does nothing, as in an app's own pages on WeChat, and the console says why once.
- A `<movable-view>` with `scale` scales with a two-finger pinch (or the mouse wheel) on it, between `scale-min` and `scale-max`, firing `scale`; with `scale-area` on its `<movable-area>`, a pinch or wheel anywhere in the area scales it.
- `<open-data>` shows "微信用户" for `userNickName` and a gray avatar for `userAvatarUrl`, as WeChat does since base library 2.27; the other user data and `groupName` are empty, so it shows `default-text` and fires `error`.
- The WeChat Shop components, newer than the reported base library 3.5.0, draw cards with the ids they are given, since the simulator has no shop data, and say so once in the console. A tap on `<store-product>` (also with `custom-content` and `logo-position`), `<store-home>` or `<store-coupon>` (with `custom-style`) fires `entersuccess`, or `entererror` without its required ids; `<store-gift>` fires `success`, or `error` -1001 without `present-order-id` and `open-id`.
- `<official-account-publish>` (3.9.3) has no posts to load: it fires `empty` and shows `placeholder` under the `#topic`; posting adds the user's post, up to `limit` before "查看更多", and fires `publishsuccess` with a simulated `postUrl`. `<reward>` (3.17.5) shows the like button in its `theme`, then "1 人喜欢" once the user likes; a `width` below 85, or a second `<reward>` on the page, shows none.
- `<selection>` (3.6.4) fires `selectionchange` for the selection in the `<text>` and `<rich-text>` with `user-select` inside it: `firstNodeId`/`lastNodeId` are those units' ids and the offsets count characters in them, empty for a boundary outside the component, and `firstRangeRect` is the first line of the selection. Its SelectionContext from `NodesRef.context` sets the selection with `selectRange` over the units' joined text or `setBaseAndExtent` by unit id, and clears it with `removeSelection`. `disable-context-menu` hides the browser's menu in it.
- `<share-element>` pairs an element in the page with one in a `<page-container>` by `key` (or the older `name`). When either has `transform`, opening the container flies the container's element from the page element's place to its own, and closing it flies the page element back, over `duration` with `easing-function`. The flying content goes to the top layer, above the overlay and unclipped by the panel, while both elements keep their room and the other one hides.
- `EditorContext.insertCustomBlock` (3.7.11) inserts an empty custom block as a line of its own and answers its `blockId`; unless `nowrap`, the cursor goes on to an empty line after it. The `<editor-portal>` whose `key` is that id stays where the template puts it and is anchored over the block with CSS anchor positioning, and the block takes the portal's height. The html keeps the block as `<div data-block-id>`, and the delta as `{ insert: { customBlock: { blockId } } }`, since WeChat documents only that the delta keeps the id.
- The EditorContext selection methods of 3.7.11 count positions as Quill does: `getSelection` gives the range (the remembered one after a blur) with its `bounds`, `setSelection` selects and focuses, `getBounds` measures any range, and `deleteText` deletes one without moving the focus, moving a later selection back with the text. Bounds are viewport `left`, `top`, `width`, `height`, `right` and `bottom`; a cursor on an empty line gets the line's height at its start. `getHistoryState` (3.9.3), whose result WeChat does not document, answers `canUndo` and `canRedo` from the editor's undo and redo stacks.
- `<slider>` draws its own 2px track and round block (`activeColor`, `backgroundColor`, `block-size` 12 to 28, `block-color`, and the older `selected-color` and `color`). `changing` fires only while the block is dragged; a tap on the track moves the value with `change` alone, as on WeChat.
- `<camera>` shows a generated preview once it has `scope.camera`, mirrored for `device-position="front"` and brighter for `flash="torch"`. With `mode="scanCode"` (read when it is inserted), tapping the preview is the camera seeing the code that `wx.scanCode` reads (`config.scanCode`), and fires `scancode` with `type`, `result`, `charSet` and `rawData`. Going to the background fires `stop`, and coming back shows the preview again. `onCameraFrame` frames are 144×192, 240×320 or 480×640 for `frame-size` small, medium and large.
- A long press (350 ms) on an `<image show-menu-by-longpress>` opens WeChat's image menu (发送给朋友, 收藏, 保存图片, 搜一搜) after `longpress`, and no tap follows; the items only show WeChat's toasts, the Mini Program hears nothing of them, and codes in the image are not recognized. `binderror` reports `GET <src> 404 (Not Found)` whatever the server answered, as WeChat does.
- `<root-portal>` (unless `enable` is false) is shown in the browser's top layer, fixed at the top left of the page, so a transformed or clipping ancestor such as a swiper-item, a movable-view or a scroll-view neither moves nor cuts it; it stays where it is in the tree, so events bubble and styles apply as before. A picker's sheet joins the top layer when it opens, so a picker inside a portal opens over it.
- Skyline components: the simulator renders pages as WebView does (`wx.getSkylineInfo` reports no support). A Skyline tag the page does not name as one of its own components renders as a built-in. `<grid-view>` follows WeChat's WebView implementation: `type="aligned"` is a CSS grid of `cross-axis-count` columns (or as many as keep each within `max-cross-axis-extent`), and `type="masonry"` puts each child, in order, in the column that ends highest; both take `main-axis-gap`, `cross-axis-gap` and `padding`. The others (`list-view`, `sticky-section`, `sticky-header`, which sticks to the top, `draggable-sheet`, the builders, `snapshot`, `span`, the gesture handlers and so on) render their children as plain containers, the gesture handlers without a box of their own, and log once that they work only in Skyline.
- `<picker mode="region">` offers every province, city and district of China's statistical division codes (2023, from [modood/Administrative-divisions-of-China](https://github.com/modood/Administrative-divisions-of-China)), with their 6-digit codes; a municipality's second column is the municipality itself. `level="sub-district"` adds a fourth column of streets (9-digit codes), which the view loads from `/__omr/region-streets` when a district needs them. `postcode` is the province capital's, since no public table gives one per district. `packages/renderer/scripts/generate-regions.ts` regenerates both data files.
- Forms: a reset clears inputs, unchecks boxes, moves sliders to `min` and returns pickers to their mode's default (selector `0`), which is also what a picker without `value` submits. A `bindinput` handler that returns a string or number replaces the field's value, unless the user typed on before the answer arrived. A `<label>` passes taps to its first button, checkbox, radio, switch, input or textarea, or to the control its `for` names in the same template.
- The shell draws the window around the page: the tab bar (badges, red dots, `setTabBarStyle`, `setTabBarItem`, `hideTabBar`, which gives the page the tab bar's height), the navigation bar (loading indicator, the home button on a first page other than the home page or a tab) and pull-down refresh, which slides the page over the window background (`backgroundColor`, `backgroundTextStyle`) with three dots until `wx.stopPullDownRefresh`.
- **Background and foreground.** The capsule's close button leaves the Mini Program, as on WeChat: the top page's `onHide` (and `pageLifetimes.hide`), then `App.onHide` and `wx.onAppHide` (`{}`; `reason` arrives in base library 3.5.7). The device then shows WeChat's recent Mini Programs; tapping this one comes back with scene 1089: `App.onShow` and `wx.onAppShow` get the top page's path and query, which `wx.getEnterOptionsSync` then returns, and the page's `onShow` follows. The pages keep running and are not suspended after five seconds, and a long absence never destroys the app.
- **DarkMode.** The system theme is light unless the URL has `?theme=dark`. With `"darkmode": true` in app.json, `themeLocation`'s theme.json resolves `@variables` in the window settings (`navigationBarBackgroundColor`, `navigationBarTextStyle`, `backgroundColor`, `backgroundTextStyle`, `backgroundColorTop`, `backgroundColorBottom`) and the tab bar (`color`, `selectedColor`, `backgroundColor`, `borderStyle` and item icons); `wx.getSystemInfoSync().theme` and `wx.getAppBaseInfo().theme` report the theme; built-in components (buttons, inputs, pickers) take dark defaults; and a change reaches `App.onThemeChange` and `wx.onThemeChange`. Without `darkmode`, the theme is `undefined` and changes are not heard. Either way, WXSS `@media (prefers-color-scheme: dark)` follows the theme, since the shell sets the page iframe's `color-scheme`, and WeChat's own dialogs turn dark. Changes made with `wx.setNavigationBarColor`, `wx.setTabBarStyle` and `wx.setTabBarItem` survive a theme change.
- **Controls.** Buttons above the device switch the theme and leave or come back. Automation can call `window.omr.setTheme("dark")`, `window.omr.appHide()` and `window.omr.appShow(scene)` in the shell, or press the buttons by their `data-omr-action` (`toggleTheme`, `toggleBackground`, `appHide` on the capsule's close button, `appShow` on the recent entry). `<html>` carries `data-omr-theme` and `data-omr-app-state` (`foreground` or `background`).

## Simulated login and authorization

WeChat DevTools signs `wx.login` and the user-data APIs with the developer's own WeChat account. The simulator stands in for that account with a configurable user, so login flows run without QR codes or network access to WeChat:

- `omr.config.json` next to `project.config.json` (or `app.json`) sets the user (`auth.user`: openid, unionid, nickname, avatar, phone number), the permissions already granted (`auth.authSetting`), whether the user has agreed to the privacy guide (`auth.privacy.agreed`, false by default as for a new user) and its name (`auth.privacy.contractName`), whether system dialogs are shown or answered automatically (`auth.consent`: `ask`, `allow` or `deny`), and initial storage (`storage`), which injects a logged-in session so a page can be opened without going through login.
- `wx.login` and the `getPhoneNumber` button return codes that encode the user. The simulator serves a mock of the WeChat server APIs (`jscode2session`, `getuserphonenumber`, `token`) at `/__omr/wechat-api`; a backend uses it in place of `https://api.weixin.qq.com` to exchange the codes. Codes expire after five minutes and are single use, as on WeChat.
- User data follows base library 3.5.0, the version the simulator reports:
  - `wx.getUserProfile`, `wx.getUserInfo` and the `getUserInfo` button return the anonymous user "微信用户" with a gray avatar and show no dialog. `wx.getUserProfile` and `wx.openSetting` still fail outside a tap handler with `can only be invoked by user TAP gesture.`; the tap state lasts through the handler's microtasks and the callbacks of `wx.login`, `wx.getSetting` and `wx.request`, and is lost after `setTimeout`.
  - The configured nickname and avatar reach the Mini Program only when the user picks them: the `chooseAvatar` button's sheet, and the bar WeChat shows above the keyboard of `<input type="nickname">`. `bindnicknamereview` fires after blur and always passes.
  - Privacy APIs (`getUserProfile`, `getUserInfo`, `getLocation`, `authorize` and the `getPhoneNumber`, `getRealtimePhoneNumber`, `chooseAvatar` and `getUserInfo` buttons) wait for the privacy guide to be agreed. The Mini Program's `wx.onNeedPrivacyAuthorization` listener is asked first; `resolve({ event: "agree", buttonId })` passes only after the `agreePrivacyAuthorization` button with that id was tapped. Without a listener, WeChat's own privacy popup asks; a refusal fails the call with `privacy permission is not authorized` and errno 104, and calls in the next ten seconds fail the same way without asking. Until the guide is agreed, `<input type="nickname">` is a plain text input. `wx.getPrivacySetting`, `wx.requirePrivacyAuthorize` and `wx.openPrivacyContract` are available, and combined open-types such as `getPhoneNumber|agreePrivacyAuthorization` record the agreement before the phone number dialog.
  - `wx.authorize` asks once per scope, remembers the answer for `wx.getSetting`, and returns success without asking for `scope.address`, `scope.invoiceTitle`, `scope.invoice` and the withdrawn `scope.userInfo`.
  - `wx.openSetting` and the `openSetting` button open the settings page (设置), with a switch for each scope the Mini Program has asked for; going back resolves with the changed `authSetting` (`bindopensetting` adds `errMsg: "openSetting:ok"`). With `auth.consent` `allow` or `deny`, it returns the current settings without showing the page.
- Other button open-types: `getPhoneNumber` adds opaque `encryptedData`, `iv` and `cloudID` next to `code` for older backends (they do not decrypt). `contact` opens a customer service chat (客服消息), with the `send-message-*` card when `show-message-card` is set; `bindcontact` fires when the user goes back, with `path` and `query` from the card's `send-message-path` if they tapped it (empty otherwise) and `errMsg: "enterContact:ok"`. `launchApp` always fires `binderror` with `{ errMsg: "invalid scene" }`, since the simulator is never opened from an app (scene 1069). `feedback` opens the 意见反馈 page and fires nothing. `liveActivity` fires nothing.
- While the Mini Program uses the location, the microphone or the camera, the capsule shows their icons in place of its dots, as WeChat does: for three seconds after `wx.getLocation`, between `wx.startLocationUpdate` and `wx.stopLocationUpdate`, while `RecorderManager` records, and while an authorized `<camera>` is on a page. `<camera>` shows a simulated preview and fires `initdone`, or `binderror` with `insertCamera:fail auth deny`; recordings stop with a `http://tmp/` path and no audio.
- System UI (the privacy popup and guide, authorization, phone number and avatar dialogs, the nickname bar, the settings, customer service and feedback pages) is drawn by the shell, outside the page's WebView. Its buttons have `data-omr-action` attributes, so automation can answer them.

CLI commands map one to one to MCP tools and print JSON by default:

| `omr dev <project>`                                                                      | Start the simulator server for humans debugging in a browser                                                           |

## Reproducibility

Agents compare screenshots to judge their changes, so rendering must be stable:

- Fixed device parameters (screen width, pixel ratio, safe area, status bar height), defaulting to a common phone model.
- Bundled open-source CJK fonts, independent of the sandbox's system fonts.
- Before a screenshot, wait for the `setData` queue to drain and images to load, with an option to disable animations.
- Launch Chromium with `--disable-features=IsolateSandboxedIframes`. Otherwise Chromium renders the sandboxed page iframes in their own process, which does not receive an emulated device scale factor, and page content is captured at 1x while the shell is at 2x.
- Time, randomness and network responses can be fixed or mocked through a config file.

## Compatibility principles

- WeChat's **observable behavior** is the reference. Implement independently from public documentation; never use proprietary code or assets from the WeChat base library or DevTools.
- Cover the rendering paths agents hit most first: WXML template syntax, WXSS, common built-in components, page lifecycles and routing, and `setData`.
- Native components (`map` without map data and the like) and capabilities that depend on Tencent services (login, payment, cloud development) are provided as placeholder rendering and configurable mocks, without aiming for real behavior.

## Non-goals

- Replacing every feature of WeChat DevTools (upload, preview, real-device debugging, profiling and so on).
- Pixel-perfect parity with the WeChat app.
- Running Mini Programs in production.
